Run scripts off the main actor, capture stderr, and terminate the child process when the hard timeout expires.
7. **`EvalCLI`** is in the repo layout and Testing section but has no task ID. *Interim:* T01 created a stub executable that prints "not implemented yet".

Keep fixture content local and sanitised; do not commit private email content to the repository.
8. **`FetchMail.js` output shape.** "Missing ids are skipped and reported", but the spec doesn't say how they're reported. *Interim:* `{"messages": [...], "missing": ["id", ...]}`; the decoder also accepts a bare array.
   - **Decision:** Confirm this output contract. `FetchMail.js` returns an object with `messages` and `missing`; `MailJSONDecoder` continues accepting the legacy bare-array form for compatibility. 9. **VIP vs blocked sender.** If a sender is on both lists, which wins? *Interim:* VIP wins ("VIP senders always land here"), and VIP also overrides the info-only signals. Block lists match exact addresses only (no domain wildcards).
   - **Decision:** Use this precedence, from highest to lowest: **Blocked → VIP → Ignored → Trusted Newsletter → ordinary bulk/newsletter → normal mail**. A blocked address is always excluded, even if also VIP. VIP overrides learned ignores and bulk/info-only signals, but not an explicit block. A trusted-newsletter rule overrides bulk-only classification so the sender can produce suggestions, but it does not override a block or an ignored-sender rule. Block and sender-list matching remain exact-address only; do not add domain wildcards.
10. **`Auto-Submitted: no`** means a human sent the email (RFC 3834). *Interim:* only values other than `no` count as info-only.
   - **Decision:** Confirm the interim rule. Compare the trimmed header value case-insensitively: a missing or `no` value is not an automated/bulk signal; any other non-empty `Auto-Submitted` value is an info-only signal.
11. **"Bare tracking URLs" in the cleaner.** *Interim:* only lines that are nothing but a URL get removed; URLs inside sentences stay, so evidence can still match verbatim.
   - **Decision:** Retain bare URLs by default because a link may be the actual task or evidence. Remove a URL line only when it can be positively identified as tracking-only (for example, a known tracking/redirect host or a URL whose meaningful content is only recognised tracking parameters). For destination URLs, strip only recognised tracking parameters when safe and preserve the destination. Do not blanket-delete URL-only lines or strip arbitrary/unknown query parameters; keep URLs embedded in prose.
12. **`{today_iso}` in the prompt.** *Interim:* the date only (`2026-11-04`). Adding the weekday ("Wednesday") would probably help the model resolve "this Friday"; should I add it?
   - **Decision:** Include the English weekday as well as the ISO date and timezone, for example `Today is Wednesday, 2026-11-04, timezone Australia/Brisbane.` Keep the ISO date as the unambiguous reference and use the existing `en_US_POSIX` locale so weekday names are stable and do not depend on macOS display language. 13. **Rule 3 "date or time words".** *Interim:* weekday and month names (plus 3-letter forms, with "may" counted only next to a number), relative words (today, tomorrow, week, weekend, morning, …), time patterns (5pm, 17:00) and date patterns (9/11, 2026-11-09, ordinals). Do not treat `ASAP` by itself as a concrete date/time. Add unit tests for the new phrases and false positives. 14. **Title length.** The prompt asks for under 60 characters, but validation allows 3 to 80. *Interim:* both kept as written; the validator accepts up to 80.
   - **Decision:** Keep the prompt's preference for concise titles under 60 characters, while treating 80 characters as the hard maximum. The validator and UI continue to accept 3–80 characters; update prompt wording to make the preference-versus-limit distinction explicit.
15. **Stopped jobs.** `JobState` has no "stopped" case, but a stopped job must stay resumable from the job list. *Interim:* Stop cancels the in-flight email, requeues it, and leaves the job `.paused` with `autoPaused = false`. Should there be a separate `stopped` state?
   - **Decision:** Add a distinct `.stopped` `JobState`. A user-initiated Stop cancels the in-flight model request, returns that email to `queued`, and persists the job as `.stopped` after the loop exits. `.paused` remains a temporary suspension; `.stopped` records an explicit user decision to end the current run. Both states are manually resumable from Past Jobs, but a stopped job is never automatically resumed. If the app exits while a job is `.stopping`, launch recovery should restore it as `.stopped`, not `.paused`.
16. **25-suggestions-per-digest cap with Backlog jobs.** A 1,000-email backlog would be cut to 25 suggestions. *Interim:* the cap applies to Daily digests only; Backlog results are reviewed in batches of 50 emails (T19).
   - **Decision:** The Daily limit of 25 is a presentation limit, not a data-generation, persistence, or deletion limit. Keep every suggestion that passes validation; show the 25 highest-confidence suggestions first and make any additional suggestions accessible in an expanded/secondary view. Never discard suggestions or mark their source emails processed merely because the display threshold has been reached. Backlog has no digest-wide suggestion limit; its results remain grouped into review batches of 50 source emails. Keep the existing limit of 3 suggestions per ordinary email. For a sender explicitly configured as a trusted newsletter source, allow up to 8 actionable suggestions from that email.
   - **Newsletter policy:** Bulk-mail headers such as `List-Unsubscribe` should identify a newsletter for classification, not automatically imply that its content has no actionable tasks. Ordinary newsletters remain summary-only. Add a separate trusted-newsletter sender allowlist (not the VIP list): a trusted newsletter produces both its normal `InfoItem` summary and task suggestions, subject to the same evidence/date/confidence validation and user approval as other mail. The trusted-newsletter rule itself must not override blocked/ignored-sender filtering. Apply the 8-item limit in both the extraction JSON schema and validator so the model and application enforce the same bound. VIP/block precedence remains governed by Q9.
17. **One digest per job.** *Interim:* each job writes one `Digest` with `Digest.id == Job.id`, re-saved after every email, so a resumed job keeps appending to the same digest.
   - **Decision:** Keep one logical digest per job and keep `Digest.id == Job.id`, including across pause/resume. However, persist each email's extraction results and skip/outcome records incrementally as child records (or an equivalent per-email persisted representation), rather than serialising and upserting the entire growing `Digest` after every email. `DigestStore.digest(id:)` should reconstruct the aggregate digest from those records when requested. Persist each email's result atomically so a crash or pause cannot leave a partially appended email result.
18. **Sender and subject per suggestion.** `Digest` doesn't store each email's sender or subject, but decisions need the sender and Reminders notes need both. *Interim:* review functions take an `emailID → EmailContext {sender, subject, mailbox}` lookup that the app builds from `job_item` rows. Should `Digest` (or `InfoItem`) carry them?
   - **Decision:** Keep sender, subject, and mailbox in `job_item`; do not duplicate these email-level fields in `Suggestion`, `InfoItem`, or `Digest`. Build the `[emailID: EmailContext]` lookup from the owning job's items when presenting or acting on a digest. The GRDB retention policy must keep the owning job and its `job_item` context for at least as long as its digest or any pinned/retained item can still be reviewed, opened, or used to create a Reminder. Delete the digest and its dependent job context together when retention finally permits deletion.
19. **Category tag edits.** `Suggestion` has no `category` field, yet the panel lets the user change it and `ReminderWriter.write` takes one. *Interim:* the category defaults to the email's `InfoItem` category, and an override is kept in `ReviewState` (not persisted). Should `Suggestion` get a `category` field so edits survive a restart?
   - **Decision:** Add a persisted optional `category: Category?` field to `Suggestion`. Set it to the model-extracted email category when suggestions are created. When the user edits the category, update and persist the `Suggestion` through `DigestStore.update`; do not keep the authoritative value only in transient `ReviewState.categoryOverrides`. Remove `categoryOverrides` once the persisted field is wired through the review flow. For older records or a missing category, resolve in this order: `Suggestion.category`, the matching `InfoItem.category`, then `.other`. This preserves category edits across app restarts and failed Reminder-write retries.
20. **Decisions keyed by address.** *Interim:* `Decision.sender` stores the lowercased address (`justin@x.com`), not "Name <addr>", so rule 7 and learned rules match regardless of display name.
   - **Decision:** Confirm address-based identity. Normalise the sender to the trimmed, lowercased email address and store that value in `Decision.sender`; never key a decision by the display name or the full `Name <address>` representation. Keep the decision outcome (for example, approved versus dismissed) distinct so future learned rules can use the actual user decision.
21. **Retention and pinned items.** "Pinned info items are kept regardless." *Interim:* a digest that contains a pinned item is never deleted. Only `finished`/`failed` jobs are deleted (paused ones are resumable).
   - **Decision:** Use a default retention period of 90 days, with user-selectable 30, 90, 365 days, or forever. A pinned item keeps its digest and the owning job plus `job_item` context required by Q18. Retention must delete or retain the digest and its dependent job context together; it must never leave a retained digest without the sender/subject/mailbox data needed to review it or create a Reminder. Paused and stopped jobs remain resumable and are not eligible for ordinary finished-job cleanup. Delete-all must preserve pinned digests and their associated context, as well as unfinished/resumable jobs. Processed-email history and sender decisions are not removed by digest retention.
22. **Retry counting after "Pause now".** `attempts` increments each time an item starts, so cancelled attempts also count toward the 3-attempt limit. Only real errors can mark an item failed, but an item paused twice and then hit by one error fails. Acceptable for v1?
   - **Decision:** Count only genuine per-email processing failures toward the three-attempt limit. Starting an item must not consume an attempt; cancellation caused by Pause, Stop, or app termination/recovery must not increment the failure count. Increment the count when an actual item-level processing error is recorded. Provider-wide/infrastructure failures follow Q25 and do not consume an item's retry budget.
23. **Daily window start.** `store.lastRunDate()` is the newest digest date, and a Backlog digest would move it, making the next Daily job skip mail. *Interim (T08):* `startDaily()` starts at the newest `scopeTo` of earlier Daily jobs (not failed), else `now - 48h`, and never earlier than `now - 48h`. `lastRunDate()` is no longer used by the runner.
   - **Decision:** Keep a Daily-specific cursor based on the greatest `scopeTo` among persisted Daily jobs that progressed beyond `.listing`, excluding `.failed` jobs. Calculate the next start as `max(lastDailyScopeTo, now - lookbackCap)` (48 hours by default). Backlog jobs must never advance or otherwise affect this cursor. A paused or stopped Daily job keeps its queue and remains manually resumable from Past Jobs; the next scheduled Daily run does not silently resume that old job. If a Backlog job is running when Daily is due, pause it, run Daily first, then automatically resume that Backlog job when Daily finishes in the same app session. A queued Backlog job persists across app restarts and can be resumed manually. Daily does not automatically discover or gradually consume all historical mail: the user must create and confirm a Backlog job for that scope. Once created, its unprocessed items remain in the persisted queue and visible in that job's progress/Past Jobs until resumed and completed. Historical mail not yet added to a Backlog job remains in Mail.app and is not represented as queued work in Mail Digest.
24. **Empty jobs and `DigestStore.digest(id:)`.** *Interim (T08):* a job that queues nothing writes no digest and posts no notification (so an empty Daily run doesn't replace the real latest digest). A resumed job reloads its digest through a new `DigestStore.digest(id:)` (a required method with no default, so the SQLite store must implement it).
   - **Decision:** Confirm this behaviour. A job with no queued work creates no digest and posts no completion notification, so an empty Daily run cannot replace the latest meaningful digest. Once a job has actually processed items, persist its digest even when it contains no suggestions, provided it contains meaningful recorded outcomes such as skipped items. Add `DigestStore.digest(id:)` as a required store method and use it to restore the same logical digest when resuming a job.
25. **Mail or store failure mid-job.** *Interim (T08):* a thrown fetch or store error ends the loop with the job in `.failed` and the queue intact; `resume(jobID:)` accepts a `.failed` job by id, while `resume()` without an id only picks `.paused` jobs. The `.validating` stage is never reported because the pipeline is a single call.
   - **Decision:** Add a provider health preflight before a job begins processing (and re-check when resuming after a job-level provider failure). Use `LLMClient.healthCheck()` to detect an unavailable Ollama service or missing model before repeatedly submitting individual emails. Treat connection failures, provider-wide timeouts, authentication/configuration problems, missing models, and provider-wide service errors as job-level failures: stop the job, persist it as `.failed` with a useful error, leave the current item queued, and do not consume that item's retry budget. The user can fix the provider and resume the failed job by ID. Reserve per-item retries for failures attributable to processing a particular email or its response (for example, malformed/invalid extraction output). Keep the queue intact on fetch/store failures as well. Do not report `.validating` as a separate progress stage while validation remains inside the single pipeline call.
26. **Preview counts and the Daily cap (T20).** `alreadyProcessed` counts processed or already-queued mail among non-excluded found emails; `totalFound` counts unique ids in range, including excluded ones. `dateRangeFound` covers all found mail, not only what will be queued. *Interim:* as stated; say if the sheet should show the range of the queued mail instead.
   - **Decision:** Keep those definitions and keep `dateRangeFound` based on all mail found in the selected scope. Add a `deferredByLimit` count for otherwise eligible, non-excluded, not-already-processed/not-already-queued emails that fall beyond the Daily `maxEmailsPerRun` cap. `toProcess` is the exact set/count that will be queued now; the Start action must state that count and make the deferred count visible. Do not confuse this Daily email-processing cap with Q16's 25-suggestion presentation threshold.
27. **Estimated speed history (T20).** "Rolling average" for the preview uses the last 20 `done` items (by `finishedAt`) across all jobs; skipped and failed items are ignored, as in the runner's own ETA.
   - **Decision:** Confirm the v1 calculation: use the 20 most recent `.done` items across all jobs, ordered by `finishedAt`, and exclude skipped and failed items. Estimate remaining time as that average processing duration multiplied by the number of queued items. If the app later supports materially different providers/models or hardware profiles, consider separating the history by processing profile; do not add that complexity for v1.
28. **Retry failed (T20).** `retryFailed(jobID:)` throws `alreadyRunning` while any job runs, and puts a finished job back to `.paused` before resuming it. Failed items marked "failed: ..." are removed from the digest's skipped list and `emailCount`. *Interim:* a failed job later resumes like any other.
   - **Decision:** Keep `retryFailed(jobID:)` for explicitly retrying per-item failures, and keep `resume(jobID:)` for resuming a job stopped by a provider/infrastructure failure under Q25. When requeuing a failed item, reset its attempt/failure count to zero and clear stale `outcome`, `seconds`, and `finishedAt` values so the queued item does not still appear completed or failed in activity views. Retain `lastError` for diagnostics until the next attempt actually starts, then clear it. Remove the item's `failed: ...` entry from the digest's skipped results and adjust the digest email count consistently; transition the finished job back to `.paused` and resume it through the normal runner path. Continue to reject `retryFailed` while any job is running.

## Additional decisions — Apple Mail T11-A review (2026-11-06)

29. **Canonical Message-ID in JXA.** T11-A found that `message.messageId()` may return `Resent-Message-ID` instead of the RFC `Message-ID` header (316 of 2,555 iCloud inbox messages on the test Mac). *Decision:* The canonical application identity always comes from the actual RFC `Message-ID` header, not JXA's `messageId()` property and never `Resent-Message-ID`. In `ListMail.js`, read the `Message-ID` header element in a batch alongside other metadata and verify positional alignment. Messages without a usable `Message-ID` remain explicit missing-identity/unsupported outcomes for v1. Before relying on `FetchMail.js` or any mail action to locate a message by canonical ID, test messages containing both headers; verify the returned raw `Message-ID` before accepting a body or mutating a message. The lookup behaviour was not proven by T11-A, so do not assume `whose({messageId: canonicalID})` is safe.
30. **JXA date filtering strategy.** The SPEC previously split large JXA date ranges into smaller `whose` windows; T11-A found that this was much slower and a 400-day listing timed out twice at 120 seconds. *Decision:* For a JXA listing, read the whole mailbox's required metadata property arrays in batches, filter the requested `[from, to)` range inside the script, and return newest-first results. Do not use JXA `whose` date predicates or date-window splitting for the listing path. Keep the 120-second hard process timeout (Q6) and the 60-second/3,000-message performance target distinct. Index-based paging may be explored for very large mailboxes, but is not a v1 requirement or an approved implementation until separately tested.
31. **Usability of `.partial.emlx`.** T11-A found a non-empty text part in every partial file scanned on this Mac, but upstream has observed partial files with empty bodies. *Decision:* Do not reject a file solely because its extension is `.partial.emlx`. Use it when the byte-count/container structure is valid and MIME parsing yields a non-empty, decodable text body without structural or truncation errors. Fall back to JXA when no usable text part exists, the counted content is truncated, MIME parsing fails, or decoding is not trustworthy. Record whether each body came from `.emlx`, `.partial.emlx`, or JXA. A non-empty part is a usability criterion, not proof that every attachment was downloaded; attachments remain out of scope for v1.
32. **Duplicate canonical Message-IDs within a mailbox listing.** T11-A found 45 repeated Message-IDs in 2,555 iCloud inbox rows. *Decision:* Deduplicate by canonical RFC Message-ID within each mailbox listing before enqueueing. Keep the row with the newest `date_received`; if timestamps tie on SQLite, keep the greatest `storeRowID`/ROWID. JXA has no equivalent ROWID, so because Mail's collection was observed newest-first, keep the first occurrence and preserve Mail's stable order for ties. Both paths must produce the same unique canonical ID set. Do not use ROWID as the cross-run identity or as a substitute for Message-ID.
33. **Active-account filtering and display names without Automation.** T11-A found 46 live rows under an `OrphanedAccount` directory that no longer appears in `Mail.accounts()`, and `AccountsMap.plist` was absent. *Decision:* When Automation is available, use the account UUID set from `Mail.accounts()` as the authoritative active-account set and use `account.name()` for display names. Without Automation, use a best-effort local-store heuristic: include UUID account folders present under the active Mail store root, exclude folders named `OrphanedAccount - <UUID>`, and show `Account (<short UUID>)` when a friendly name is unavailable. Do not depend on `AccountsMap.plist`. Preserve `local://` / On My Mac mailboxes; they are not UUID account folders. Enumerate nested JXA mailboxes top-down rather than assuming account mailbox arrays expose full nested paths.
34. **Timing of real-app permission validation.** T11-A could not verify FDA or Automation through the Mail Digest app because it was ad-hoc signed, had no Development Team configured at investigation time, and had no in-app capability probe. *Decision:* Move this check to the start of T11-C, after configuring a real Apple Development signing identity and Development Team. Verify both permissions through the actual signed `dev.pages.justinwang.maildigest` application; Terminal/Xcode-host permission observations alone do not satisfy the check. This is a scheduling change, not a waiver: real-app FDA/Automation validation remains required before T11-C is complete.

## Found during T11-D (2026-11-06)

35. **Long emails versus the 180-second Ollama timeout on Intel CPUs.** The spec sets a 180-second request timeout, `num_ctx: 8192`, and truncation of the cleaned body at 24,000 characters. On the target Mac (i7-9750H, CPU only, Ollama 0.40.14, `qwen3:4b`), one real 12,800-character email became 7,725 prompt tokens. Ollama needed 756 s for prompt evaluation and 875 s in total, so `OllamaClient` timed out and the email produced no result. Short emails are unaffected. The current runner treats a timeout as an item failure (up to 3 attempts × 180 s), so one long email can add up to 9 minutes. Q25's job-level provider-failure handling is not implemented in `JobRunner` yet. *Interim:* nothing changed. The spec values are kept and the result is recorded in `docs/T11-C-VALIDATION.md`. Options: a lower character cap for the prompt (for example about 6,000 characters ≈ 2,000 tokens) with the existing `[truncated]` marker; a longer timeout for prompt evaluation; or both. Any change would also affect evidence validation, which matches against the text the model saw.
   - **Decision:** Raise the `extract()` request timeout to 1,000 seconds. Keep `headline()` at 180 seconds and `healthCheck()` short (10 seconds). Do not reduce body limits or add truncation, chunking or multi-stage extraction. Keep `think: false`. Do not retry the same long-email timeout automatically: a timed-out extraction fails the item after one attempt, and manual retry (`retryFailed`) remains available. Provider-wide failures are handled at job level under Q25.

## Found during T16 (2026-11-06)

36. **Do approvals affect the learned ignore suggestion?** The spec says to suggest ignoring a sender "after 5 dismissals from one sender". *Interim (T16):* `IgnoreRuleSuggester` counts every `.dismissed` decision for the sender, ever; approvals neither count nor reset the count, and nothing expires. A sender whose reminders you often approve but sometimes dismiss can still reach 5. Options: keep as is; require dismissals to outnumber approvals; or count only dismissals since the last approval. "Not Now" is remembered for the session only; "Don't Ask Again" is stored in `declinedIgnoreSuggestions`.
   - **Decision:** Count only dismissals made after the sender's most recent approval. An approval resets the effective count to zero; there is no expiry policy. Duplicate decision rows for one suggestion still count once. "Not Now" stays session-only and "Don't Ask Again" stays persisted in `declinedIgnoreSuggestions`.
37. **`ReminderWriter.write` needs the email context.** The spec's `write(_:category:toList:)` cannot build the required notes (`From: <sender>`, `Subject: <subject>`) because the writer never receives them, and Q18 keeps sender and subject out of `Suggestion`. *Interim (T14):* `write(_:category:email: EmailContext?, toList:)`; `ReviewActions.approve` passes the email's context from the job_item lookup, and notes omit the From/Subject lines when it is nil.
   - **Decision:** Keep the T14 API accepting `EmailContext?` so Reminder notes include sender and subject.
38. **Time zone for scheduling and Reminder due dates.** The spec says the user's time zone comes from settings (default `Australia/Brisbane`), but no time zone setting exists. *Interim (T14/T15):* the morning schedule and Reminder due components use `Australia/Brisbane`, the same default as `RunnerSettings`; the Settings run-time picker stores wall-clock hour and minute.
   - **Decision:** Keep `Australia/Brisbane` as the fixed v1 time zone for scheduling and Reminder due dates (and the existing pipeline date resolution). Do not use the Mac's system time zone. A user-selectable time zone is out of scope for v1.

## Found during T18 (2026-11-06)

39. **Undo and "moved" state only last for the app session.** The spec says Undo is available until the app quits and stores the original mailbox per email, but does not say whether moved or kept emails should stay hidden from the Processed list after a relaunch. *Interim (T18):* `UndoLedger` is in memory only (as implemented in T17), so after a relaunch emails moved earlier reappear in the Processed list and moving them again reports "not found" (their location in Mail changed). Options: persist moved/kept ids in the `setting` table or a new table; or hide rows whose action reports "not found" (risky: could hide mail that was only temporarily unfindable). Not changed.
   - **Decision:** Persist explicit `moved` and `kept` dispositions in a dedicated GRDB table associated with the owning job item/digest email result, not in the global `processed_email` table or settings JSON. A successfully moved or kept email remains hidden from Processed after relaunch. Record a disposition only after the action succeeds. A successful Undo clears the corresponding `moved` disposition; Keep remains hidden and is not undoable. Never infer a disposition from a `not found` response. Delete disposition records with their owning job/digest context under the existing retention policy, while preserving `processed_email` dedupe records.
40. **Trash target uses Mail's `move`, not `delete`.** *Interim (T18):* `MailActions.js` resolves the account's Trash mailbox from Mail's own `trashMailbox` list and moves the verified message there with `Mail.move`, instead of `Mail.delete`, so the destination is known (needed for Undo) and does not depend on an account's delete behaviour. An email already in a Trash mailbox is refused ("already in Trash"). On My Mac mail has no Trash target on the target Mac, so it fails safely.
   - **Decision:** Keep the current `Mail.move` approach to the account's explicit Trash mailbox. Do not use `Mail.delete`. Refuse an email already in Trash, fail safely when no Trash destination exists (including the current On My Mac case), and retain the original mailbox so Undo can restore it.
41. **"Select all newsletters" semantics.** Every row starts ticked, so adding newsletters to the selection would do nothing. *Interim (T18):* the button ticks exactly the newsletter rows and unticks the others; "Select All" and "Select None" (not in the spec) were added so every row can be re-ticked.
   - **Decision:** Keep this behaviour: "Select all newsletters" replaces the current selection with newsletter rows only; "Select All" and "Select None" remain available to restore or clear the full selection.
42. **Auto-file scope and trigger.** *Interim (T18):* auto-file considers only the digest shown in the review panel, runs after a run finishes and after Add Selected or a dismissal (never while a job is still running, never when the setting is switched on), files blocked-sender emails too, and never retries an email it already tried or that was undone in the same session.
   - **Decision:** When auto-file is enabled, move each newly eligible per-email result into the account's Mail Digest folder as soon as that result is persisted and fully qualifies under `ProcessedEmailSelector`; do not wait for the whole job to finish. Apply this to the current logical job/digest across all review batches, not only the visible batch. Include blocked/ignored skip-tier messages when the selector considers them processed, but never move pending, in-flight, or failed items. Do not sweep historical jobs when the setting is enabled; only newly completed results in the current job/review context are eligible. Persist auto-file attempt state so relaunches cannot repeat an attempt indefinitely. Successful moves use the persistent `moved` disposition from Q39; failures are reported and are not automatically retried forever. After Undo, do not auto-file that email again automatically.

## Found during T19 (2026-11-06)

43. **Resource pauses and a manual resume or start.** The spec says Backlog jobs auto-pause on battery, Low Power Mode, heat and outside quiet hours, but not what happens when the user starts or resumes a job while a rule applies. *Interim (T19):* the policy acts when the set of blocking reasons changes, and once right after a job starts (so a Backlog job started on battery pauses after its first email with "battery power" and resumes when plugged in). A job the user resumes by hand while a rule still applies keeps running until the next change. Should a manual Resume override the rules until they clear, or should Start refuse to begin while blocked?

If a new Backlog job is created while blocked, persist it as paused with the blocking reason before processing any email—there must be no first-email leak. A manual Resume while a blocker remains active leaves the job paused and reports the reason; it can run once the blocker clears under Q44's auto-resume rules. Users may change configurable battery/quiet-window settings, but Low Power Mode and serious thermal conditions remain enforced. Daily jobs continue to follow the SPEC's separate resource policy.
44. **Auto-resume scope.** *Interim (T19):* only jobs the current runner auto-paused for battery, Low Power Mode, heat or quiet hours in this session are auto-resumed. A job auto-paused in an earlier session, one paused for a Daily job (resumed by the runner chain), and anything the user paused or stopped wait for a manual Resume, in line with "paused jobs survive restarts and resume only when the user clicks Resume".
   - **Decision:** Keep same-session auto-resume only for jobs this runner auto-paused because a resource blocker became active. A resource-paused job restored after app relaunch requires a manual Resume. A Backlog job pre-empted by a Daily job resumes only through the same-session Daily/Backlog hand-off. User-paused and stopped jobs are never auto-resumed.
45. **Quiet hours semantics.** The spec says "only run 10pm to 7am". *Interim (T19):* quiet hours are an allowed window (default 10 pm to 7 am, off by default), in Brisbane time (Q38); equal start and end means no restriction; Daily ignores them. Resource rules have no other settings beyond "pause on battery" (default on) and the quiet-hours switch and times.
   - **Decision:** Keep allowed-window semantics: when enabled, Backlog jobs may run only inside the configured window (default 22:00–07:00, off by default); equal start and end means unrestricted. Daily jobs ignore this window. Rename the UI label to "Only run during this time window" (or an equally unambiguous "Backlog run window") rather than calling it "quiet hours", which suggests the opposite meaning. Continue to interpret the window in `Australia/Brisbane` time (Q38).
46. **Run Now and the setup window while a job is paused.** The old rule disabled Run Now whenever any job strip was visible. *Interim (T19):* only a running job disables it, so a paused Backlog job no longer blocks a Daily run; the scheduled Daily run also preempts a running Backlog job (core `startDaily` pauses it, then it resumes).
   - **Decision:** Keep this behaviour. A paused Backlog job does not disable Run Now or prevent a Daily job from starting. A Daily job pre-empts a running Backlog job and the Backlog job resumes after Daily finishes in the same app session, subject to Q44. User-paused/stopped Backlog jobs are not silently resumed.

   - **Decision:** Keep result-based batches of up to 50 source emails in the job's stable order (newest first). Batches fill as per-email results are persisted and never show empty placeholder pages. Selection and review actions apply only to the visible batch. Items skipped before processing and therefore lacking a persisted result do not appear in a review batch.

## Found while implementing Q39–Q49 (2026-11-06)

50. **What "newly completed" means for auto-file (Q42).** *Interim:* the settings store the time auto-file was switched on (`autoFileEnabledAt`, stamped when switched on, or on first load for settings saved earlier). An email of the shown digest is auto-filed only if its job item finished at or after that time; one processed earlier is never moved, even if its suggestions are decided later. Attempts are stored as an `autoFileAttempted` disposition before the move.
51. **Daily emails gone when a job resumes.** *Interim:* a queued Daily email that the pre-resume listing no longer finds in the job's mailboxes and scope is stored as `skipped` ("skipped: no longer in mailbox") without a digest result, and is not added to `processed_email`, so it is not reviewable and a later job could still pick it up if it reappears in a selected mailbox.
   - **Decision:** Resuming a job of either kind first *reconciles* its open (queued or processing) items against its selected mailboxes, matched by canonical RFC Message-ID. The reconciliation listing covers the job's stored scope, widened to include every open item's received date, so an item older than a new Daily discovery window is never mistaken for missing. An item still in its mailbox keeps its entry; one moved to another selected mailbox follows the move; one found in no selected mailbox is stored as `skipped` ("skipped: no longer in mailbox") with no digest result, no attempt and no `processed_email` row, as in the interim. Done, failed and skipped items and their results are never touched. Reconciliation is all-or-nothing: every listing must succeed before any item changes (see Q53). Finding *new* mail is a separate, Daily-only step (Q53); Backlog Resume reconciles only.

## Daily lifecycle and the state-aware menu action (2026-11-06)

52. **At most one unresolved Daily job; the menu's Daily action follows it.** A paused Daily job showed Resume in the menu's progress card while Run Now underneath created a second Daily job, and the scheduler ignored paused, stopped and failed Daily jobs from earlier days (and failed ones from today), so it could create duplicates too.
   - **Decision:** Completed Daily jobs are history and stay separate digests (Q17). At most one Daily job may be *unresolved* at a time: listing, running, pausing or stopping, or paused, stopped or failed with queued work left. A paused, stopped or failed Daily job with nothing queued has nothing to continue and does not count (a failed one is already excluded from the Q23 cursor, so its window is listed again). Backlog jobs never count. The state is derived from persisted jobs (with the runner's live state on top), so it holds after a relaunch.
   - `JobRunner.startDaily()` (and `start` with a Daily plan) refuses with `dailyJobUnresolved` while a Daily job is unresolved, before pre-empting any Backlog job. `retryFailed` on a Daily job is refused while another Daily job is unresolved, because it would create a second one. Nothing is deleted or merged to keep the invariant.
   - The menu's primary row: no unresolved Daily job → **Run Now** (pre-empts a running Backlog job under Q23/Q46, so it is not disabled just because a Backlog job runs); paused → **Resume**, which resumes that exact job id and queue after re-checking its state (the menu's progress card then hides its own Resume; the Review Panel, Past Jobs and a paused Backlog card keep theirs); listing/running/pausing → **Daily Digest Running…** (disabled); stopping → **Stopping…** (disabled); stopped → **Review Daily Job…** (opens Settings > Jobs; Q15/Q48 manual resume only); failed → **Retry Daily Job** (the Q25 resume-by-id path); more than one → **Review Daily Jobs…** (nothing is picked for the user). Resume and Retry of a Daily job pre-empt a running Backlog job like Run Now and hand back to it afterwards.
   - Scheduler: when the morning run is due while a Daily job is unresolved, it does not create a job and does not resume the old one (Q15, Q23); the menu says the scheduled digest is waiting. Nothing is recorded for the skipped check, so once the job is resolved the usual `isDue` rule and the Daily cursor `max(lastDailyScopeTo, now - lookbackCap)` decide; the app checks again as soon as it sees the job resolved instead of waiting for the next 15-minute check.
   - Stop on a paused job's card now stores it as `.stopped` (it did nothing before, because no loop was running).
   - Resuming the one unresolved Daily job continues that job: Q53's new-mail step appends to it (same job id and digest) and never creates a second Daily job. If another Daily job is somehow also unresolved (data from before this rule), the resume reconciles only and skips the new-mail step, so resuming can never add a second unresolved Daily job.
   - Reconciliation: Q15, Q23, Q25, Q28 and Q48 are unchanged; this adds the uniqueness rule on top. Resolving an unresolved Daily job means resuming it to completion; there is deliberately no discard action (not in the spec). If one is wanted later, it needs its own decision.

## Resume: reconcile, then discover new Daily mail (2026-11-06)

53. **What Resume does for Daily and Backlog jobs.** Before this, resuming a Daily job only re-listed its original `[scopeFrom, scopeTo)` window, so a Daily job paused overnight never saw newer mail, and a Backlog job was resumed without checking its queue.
   - **Decision:** *Daily Resume = reconcile the existing queue (Q51) + discover newly arrived mail. Backlog Resume = reconcile the existing queue only.*
   - **Daily discovery.** The resume captures `now` once (after the same "check for new mail" step a Daily start uses) and lists `[from, now)` with `from = max(lastDailyScopeTo, now - lookbackCap)`, the Q23 cursor: the greatest `scopeTo` of Daily jobs past `.listing` and not `.failed` (the resumed job counts unless it is failed), with the 48-hour default cap. The original window is never reused as the discovery window, and a pause longer than the cap never searches further back; older mail is Backlog's job (Q23). New mail goes through the same eligibility path as a Daily start (exclusions, processed and queued-elsewhere dedupe, newest first) and also skips every message already in this job in any state. Admitted mail is appended after the job's existing items, in the same job and digest (Q17). On success the job's `scopeTo` becomes the captured `now` (its `scopeFrom` stays), which advances the Daily cursor.
   - **Q26 cap on resume.** `maxEmailsPerRun` bounds what the resumed run will process: new mail admitted = `max(0, maxEmailsPerRun - open items left after reconciliation)`, newest first. Open items are never dropped, even when they alone exceed the cap (then nothing new is admitted). Eligible mail beyond the allowance is deferred and not queued, exactly as on a Daily start, and the cursor still advances. No cap means no limit.
   - **Backlog.** Reconcile only: no new-mail listing, no "check for new mail", and `scopeFrom`/`scopeTo`, mailboxes and job identity stay as the user confirmed them.
   - **Failure and consistency.** Every listing (reconciliation and discovery) and dedupe lookup runs before anything changes. If any listing fails, the resume aborts with the existing "Could not read Mail…" error and the job keeps its state (paused, stopped or failed), queue and scope. The skips, relocations, appended items and new `scopeTo` are then written in one store transaction, so repeated or interrupted resumes never duplicate or half-apply work. Resource rules (Q43, Q44) and the provider check (Q25) still run before any listing.
   - **Related rules.** Q52's one-unresolved-Daily-job rule holds: discovery only extends the resumed job and is skipped when another Daily job is unresolved. Every Resume goes through this: the Resume buttons, Retry Daily Job, `retryFailed` (Q28) and Q44 auto-resume, so a Backlog job re-lists its mailboxes over its scope each time it is resumed. The same-session hand-off back to a Backlog job after a Daily job (Q23, Q46) is a continuation, not a Resume, and does not reconcile; an email that disappeared meanwhile is still skipped at fetch time as "not found in Mail". Q26's preview `deferredByLimit` count is still not implemented and is unchanged by this decision.

## Hybrid privacy routing and Activity Center (2026-11-08)
